# DroneLab: рассказ для судей и ответы специалистам

Итог физического модуля SDK 0.3.0. Полная инженерная таблица — [PHYSICS_REFERENCE.md](PHYSICS_REFERENCE.md), источники и реальные сравнения — [REFERENCE_DRONES.md](REFERENCE_DRONES.md). Это тезисы для рассказа команды; показывать аудитории все формулы не требуется.

## Пять смысловых блоков

| Блок | Что объяснить | Что показать |
|---|---|---|
| Аппарат как физическое тело | Масса, центр масс, инерция и плечи сил определяют реакцию; внешний mesh и параметры физики разделены | Масштаб в метрах; изменение массы/COM; одинаковое управление даёт другую реакцию |
| Реальная структура привода | Отдельные роторы имеют тягу, момент, задержку, ограничения и отказ; доступны измеренные кривые винта | RPM/T каждого мотора; отказ одного двигателя с потерей устойчивости |
| Воздух и среда | Сопротивление корпуса/роторов, поток в точках, плотность с высотой, ветер и ограниченный ground effect | Спокойный hover, затем ветер и близость земли; заранее фиксированные profiles/seed |
| Энергия и ресурс | Батарея проседает, ток ограничивает тягу, заряд падает; потери создают тепло и derating | Один текущий успешный сценарий: current limit мешает взлёту, затем разряд уменьшает запас тяги |
| Проверяемый переносимый модуль | JSON с единицами/источниками, regression tests, CSV, два UPM пакета; controller и карта независимы | Benchmark результаты и импорт physics в другой проект; список известных ограничений |

Демонстрация: 1) размер/масса и нормальный hover; 2) один энергетический сценарий; 3) отказ мотора; 4) одна таблица сравнения с открытым стендом. Ветер/ground effect можно оставить для вопросов. Не запускать одновременно все аварии: зрителю должна быть понятна причина реакции.

## Рассказ примерно на минуту

Мы сделали параметрический физический модуль мультикоптера для Unity. Дрон движется от сил отдельных роторов, сопротивления воздуха и гравитации; его реакция зависит от массы, центра масс и инерции. Привод имеет динамику и ограниченную мощность: большой ток вызывает просадку батареи, разряд уменьшает запас тяги, потери нагревают моторы и ESC. Отказ отдельного мотора нарушает баланс и приводит к потере устойчивости.

Параметры хранятся в JSON с единицами и происхождением. Для независимых точек открытых стендов Bitcraze и UIUC мы сравнили тягу и коэффициенты винта, а для других аппаратов проверили перенос опубликованных моделей. Мы отделяем такое сравнение от доказательства точности полного полёта: аппаратной калибровки у нас нет. Модуль поставляется отдельно от карты, интерфейса и пилота и записывает телеметрию для дальнейшей проверки.

## На техническом слайде

Показать пять блоков выше, один скриншот telemetry и три коротких результата: Bitcraze mean 3.313% с честным low-RPM максимумом 16.153%; APC static max absolute CT error 0.0010400; APC axial 0.0008000. Подписать **«ошибка на withheld стендовых точках; не точность траектории»**. Brushless interpolation error не сравнивать с этими experimental errors как равнозначное доказательство.

Не говорить «полностью реалистичный», «сертифицированный Dryden», «симулируем VRS», «восстанавливаем всё из 3D модели», «точность 97%» или «полностью повторяем настоящий полёт». Корректно: «модуль связанных инженерных моделей с явными ограничениями, источниками параметров и воспроизводимыми проверками».

## Вероятные вопросы специалистов

| Вопрос | Ответ команды |
|---|---|
| Какая точность? | Для конкретных withheld стендовых точек есть численные ошибки в отчёте. Для полного полёта одного общего процента нет: нужны параметры аппарата, синхронные flight logs, контроллер и условия опыта |
| Это цифровой двойник трёх аппаратов? | Частичные reference профили: известные масса/инерция/привод взяты из открытых данных, оценки подписаны. Неизвестная батарея/термика/drag выключены, поэтому полного двойника не заявляем |
| Что вы действительно проверили измерениями? | Независимые точки тяги Bitcraze и CT/CP UIUC, которые не импортированы в профиль. Brushless fit и Hummingbird saturation — сверка опубликованной модели/единиц, не новые экспериментальные flight tests |
| Почему у Crazyflie ошибка 16%? | Разреженная RPM таблица плохо интерполируется на низких оборотах; максимум на 7570 RPM. Мы сохранили эту точку как holdout и публикуем ошибку. Исправление требует более плотных независимых замеров, а не сокрытия точки |
| Откуда геометрия и лицензии? | Закреплённые CF2 URDF/DAE из gym-pybullet-drones, Hummingbird visual из RotorS, schematic BrushJAX. Ссылки и лицензии перечислены; найденная визуальная модель не заменяет измеренные параметры |
| Что можно определить из mesh? | Габариты и направленные площади проекции. Масса, распределение материала, Cd, Kv, батарея и thermal коэффициенты из внешнего вида не определяются |
| Если повернуть Physics marker, поменяется ли полёт? | Только после экспорта и назначения нового JSON snapshot. Маркеры — authoring tool; runtime не сканирует их Transform |
| Можно ли другой тип аппарата? | Физика применяет силы произвольного набора роторов. Наш optional test pilot/allocator ограничен четырьмя параллельными +Y роторами. Hexa, tiltrotor или inverted layout потребуют другого controller |
| Почему Unity, а не CFD? | Нужны интерактивные сцены и инженерные сценарии с ограниченным вычислительным бюджетом. У нас Rigidbody и reduced models, а не потоковая сетка. FPS на целевых компьютерах нужно измерить; универсальной цифры производительности не заявляем |
| Есть гироскопический эффект? | Да, явный момент от углового импульса роторов и реакция разгона. Свободная прецессия асимметричного корпуса отдельно не верифицирована — интегрирование тела выполняет Unity |
| Моторы мгновенные? | Нет: FirstOrder либо инерционный Electrical режим. В последнем учитываем torque разгона, spin energy, ток и supply constraints; winding inductance/ESC коммутации нет |
| Батарея — просто таймер? | Нет: OCV(SOC), внутреннее R, ток/напряжение, расход ёмкости, энергия и нагрев; governor ограничивает достижимые RPM. Это эквивалентная модель, не электрохимия |
| Почему нельзя взять батарею из данных Bitcraze? | Их общий ток включает плату, а напряжение стенда зависит от внешнего питания/проводов. Нельзя из этих колонок без дополнительного опыта идентифицировать pack resistance и motor current |
| Что с теплом? | Эффективный узел батареи, каждого мотора и ESC: потери, обдув, heat capacity, охлаждение, температурное R мотора и derating. Нет отдельных обмоток/ячеек и модели пожара |
| Что за ground effect? | Ограниченное эмпирическое усиление положительной тяги по расстоянию и нормали поверхности с ray probe. Коэффициенты должны калиброваться; это не решение wake/terrain взаимодействия |
| Есть VRS и сложный спуск? | Есть диагностика descent/axial/lateral ratios и области применимости. Силы vortex ring state, dynamic inflow, взаимодействие следов не реализованы; потерю устойчивости нельзя автоматически назвать VRS |
| Как моделируется турбулентность? | Есть воспроизводимое bounded Fourier поле и finite-band DrydenFrozen спектр вдоль одной переносимой линии; три компоненты, retained variance и sampling warnings. Не полный 3D CFD/MIL angular-gust model |
| Дождь или снег влияют на физику? | Пока precipitation — метаданные для отображения. Налипание, масса воды, обледенение и деградация тяги не вычисляются |
| Что означает проверка энергии? | Мы сверяем shaft/propeller/spin power, terminal/chemical/battery loss и generated/rejected/stored heat. Согласованный баланс важен, но сам по себе не подтверждает реальные коэффициенты |
| Каков physics step и воспроизводимость? | Используется FixedUpdate/явный шаг; pure модели имеют timestep tests, например мотор 5/10/20 мс. Ветер повторяется по seed. Для всех полётов и разных платформ побитовой PhysX идентичности не обещаем |
| Настоящие датчики и автопилот? | Demo стабилизатор читает идеальное состояние Rigidbody. IMU/GPS noise, задержки, EKF, radio/firmware не моделируются. Route autopilot будет отдельным модулем поверх motor command API |
| Почему нужно несколько acceptance profiles? | Combined synthetic проверяет связность всех модулей; отдельные стенды локализуют регрессии; реальные частичные profiles проверяют то, для чего есть данные. Это разные задачи, не дублирующая проверка абсолютной точности |
| Что осталось проверить? | Установку SDK в чистый Unity проект, PlayMode и EXE на машинах команды; далее независимые flight datasets. Здесь core и пакетная структура проверяются без установленного Unity |
| Как карта/меню используют физику? | Подключают Physics UPM, загружают JSON, отправляют motor commands и читают telemetry. Demo optional; физика не зависит от HDRP, карты, модели из Asset Store или конкретного интерфейса |
| Ваш вклад или готовая библиотека? | Параметрический core/адаптер, authoring snapshot, связность airflow/power/spin/thermal, диагностика, tests и packaging разработаны в проекте. Опубликованные параметры/геометрия используются с атрибуцией; Rigidbody solver — Unity |

## Что подготовить к выступлению

Зафиксировать один commit SDK/версии JSON, сохранить сцену и profiles демонстрации, использовать размерный ориентир, записать baseline CSV и fault/current-limit CSV. Отдельно сохранить reference-validation-results.json. На вопрос о неизвестном коэффициенте показывать provenance, а не утверждать, что он измеренный. Установка и smoke test в целевом проекте команды должны быть выполнены до выступления.
