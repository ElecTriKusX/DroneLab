# Этап 3: геометрия и аэродинамика корпуса

## Сначала проверить обновление

1. `git pull --ff-only` в ветке `physics-packages`.
2. Открыть существующую сцену, дождаться компиляции.
3. Window → General → Test Runner → EditMode → Run All, затем PlayMode → Run All.
4. Старый `quad_test_basic` оставляет прежнее сопротивление по осям. Новые режимы
   включаются назначением другого JSON или экспортом нового профиля.

Существующая сцена и модель не меняются этим коммитом. Удалять DroneTestPilot не нужно.
JSON остаётся версии 1.0.0: активированы уже предусмотренные ProjectedArea и Surfaces;
имена полей, единицы и характеристики моторов не менялись.

## Настроить роторовую геометрию своей модели

1. Остановить Play. В Hierarchy выбрать корень с **DronePhysicsBody**.
2. **DroneLab → Geometry → Create Markers from Profile**.
3. На корне появится **DroneGeometryAuthoring**, внутри — `Physics Markers`:
   `COM`, `Drag Point` и по маркеру на каждый rotorId. Маркеры ничего не толкают.
4. В Scene View включить Gizmos. Выбирать маркеры и перемещать их инструментом Move:
   Rotor — в центр соответствующего мотора; COM — в предполагаемый/измеренный центр массы;
   Drag Point — в выбранную точку приложения суммарного сопротивления.
5. Не менять Rotor Id. **Clockwise** задаёт CW при взгляде сверху для оси +Y.
   Локальная зелёная ось +Y маркера — ось тяги. Для текущего DroneTestPilot оставить
   все оси по локальному +Y корня. Произвольные оси допустимы физикой, но данный пульт
   поддерживает только четыре параллельных +Y ротора и управляемое расположение.
6. Выбрать корень. В **DroneGeometryAuthoring → Body Mesh Root** перетащить объект
   неподвижного корпуса модели, содержащий нужные MeshFilter/SkinnedMeshRenderer.
   Вращающиеся пропеллеры и отдельные LOD-копии должны находиться вне выбранной ветки.
7. Проверить физические размеры: корень и родители scale=(1,1,1); масштабировать визуальный
   дочерний объект. Экспорт учитывает его реальный local scale/rotation/position.
8. **Export Box Drag Profile** в Inspector — простой первый вариант.
   Сохранить как новый `.json` в Assets. Экспорт проверит и назначит профиль в DronePhysicsBody.
9. Сохранить сцену → Play → F → H → проверить WASD и Q/E.

Если Body Mesh Root назначен, экспорт Box/Mesh записывает размеры AABB выбранной
геометрии в `dimensionsM`. AutoBox пересчитает приблизительную инерцию по этим размерам.
Если используется ManualPrincipal, пользовательские моменты/главные оси сохраняются.
Масса, моторы, винты и их коэффициенты сохраняются. Box без Body Mesh Root использует
существующие размеры профиля. Collider не подгоняется автоматически: его размеры нужно
согласовать с моделью отдельно. Занесённые маркеры действуют только после экспорта.

## Получить площадь силуэта mesh

1. Выполнить пункты с маркерами и назначить **Body Mesh Root**.
2. Если Console просит Read/Write: выбрать исходный FBX/model asset в Project →
   Inspector → Model → Read/Write Enabled → Apply. Вернуться к корню дрона.
3. Оставить **Silhouette Resolution = 128** для первой проверки; 256 повышает детализацию.
4. Указать **Projected Drag Coefficient**. Значение 1 — стартовая оценка, не вычисление Cd.
5. **Export Mesh Silhouette Profile** → дождаться bake → сохранить новый JSON → сохранить сцену.
6. Play. В HUD появятся `Body ProjectedArea`, площадь силуэта текущего направления воздуха,
   общая сила сопротивления и аэродинамический момент.

Считается ортографическая проекция всех треугольников выбранной ветки и объединение
покрытых пикселей. Перекрывающиеся треугольники/части корпуса не увеличивают площадь
повторно. В JSON записывается LUT по 13 осям: эквивалент 26 направлений, поскольку
геометрический силуэт имеет одинаковую площадь с противоположных сторон.
В runtime mesh не обходится; используются сохранённые samples.

Bake включает активные объекты с включёнными MeshRenderer/SkinnedMeshRenderer.
SkinnedMeshRenderer фиксируется в текущей позе. Прозрачность материала/текстуры, отверстия
по alpha и положение анимированных частей не учитываются. Любые включённые LOD меши
под выбранной веткой входят в силуэт; для чистого bake выбирать одну конкретную LOD-ветку.
Мелкие детали меньше пикселя могут исчезнуть. LUT и растеризация — приближения, не CFD.
Для очень тонкой плоской геометрии с нулевым силуэтом в части направлений использовать Surfaces.

`modelScaleMetersPerUnit` остаётся метаданными исходного импорта. Экспорт берёт реальные
координаты преобразованной модели в локальных метрах корня, поэтому второй раз этот
коэффициент не умножает. При масштабировании геометрии в два раза площадь растёт в четыре.

## Отдельные поверхности

Surfaces задают несколько сил в разных точках и могут создавать сопротивление вращению.
Модель предназначена для независимых эмпирических участков, например боковых частей лучей.

1. В `Physics Markers` создать пустые дочерние объекты для участков корпуса.
2. На каждый добавить **AeroSurfaceMarker** через Add Component.
3. Указать уникальный **Surface Id**, **Area M2** и **Drag Coefficient**.
4. Переместить в точку приложения силы; повернуть так, чтобы +Y смотрела по нормали участка.
   Area M2 — физическая площадь в м², не площадь, автоматически умноженная на scale маркера.
5. На корне → DroneGeometryAuthoring → **Surfaces**: задать Size и перетащить все маркеры.
6. **Export Surfaces Profile** → сохранить новый JSON и сцену → проверить полёт.

Каждый участок двусторонний. Отдельные противоположные стороны одного физического
участка создавать не нужно — это удвоит его силу. Участки не экранируют друг друга;
подъёмная поляра, трение вдоль поверхности и CFD-давление не моделируются.
Drag Point при Surfaces не используется: у каждого элемента свой positionLocalM.

Быстрые синтетические пресеты в Resources/DronePhysics:

| JSON | Назначение |
|---|---|
| quad_test_basic | Прежний AxisApproximation, контроль совместимости |
| quad_test_projected_box | ProjectedArea по аналитическим площадям box |
| quad_test_projected_lut | ManualDirectionalLUT с 13 направлениями box |
| quad_test_surfaces | Синтетические участки для проверки сопротивления вращению |

Назначить JSON в **DronePhysicsBody → Drone Profile**. Для ветра назначить
`environment_wind` в Environment Profile. Включить H: ветер должен сносить дрон по +X.
В Surfaces при установившемся yaw возможна постоянная разница RPM: моторы теперь должны
компенсировать аэродинамический момент. ProjectedArea в COM сам по себе этого не добавляет.

## Закреплённые формулы

Все величины SI, вычисления в локальных осях корпуса. Скорость воздуха в точке:

`vPoint = vCOM - wind + omega × (point - COM)`.

При наличии вращения скорость каждой точки отличается от скорости COM.
Корпус применяет ровно одну выбранную модель; силы роторов остаются отдельно.

| Модель | Сила |
|---|---|
| AxisApproximation | Прежнее `Fj = -0.5 rho Cd_j A_j v_j abs(v_j)` |
| ProjectedArea | `F = -0.5 rho Cd A(d) abs(v) v`, `d = normalize(v)` |
| Surfaces | `vn = dot(vPoint, n)`; `F = -0.5 rho Cd A vn abs(vn) n` |

ProjectedArea с `projectedArea.mode=AxisApproximation` использует
`A(d)=Ayz abs(dx)+Axz abs(dy)+Axy abs(dz)`, referenceAreaM2=[Ayz,Axz,Axy].
Box площадью считается аналитически. ManualDirectionalLUT и MeshDirectionalLUT
используют положительные samples в м² с единичными directionLocal.
Для интерполяции `distance_i=1-abs(dot(d,di))`, `weight_i=1/distance_i²`;
площадь — нормированная взвешенная сумма. Точное попадание в sample возвращает его площадь.
Интерполяция непрерывна, положительна и не выходит за диапазон сохранённых площадей.
Это выбранная численная аппроксимация, а не точная площадь mesh между samples.
Противоположные/повторяющиеся оси samples отклоняются; допускается 1–256 samples.
Один sample подходит для постоянной площади, например πR² у сферы.

ProjectedArea прикладывается в dragApplicationPointLocalM, иначе COM.
Для Surfaces суммируются сила и момент `sum((point-COM) × F)` каждого элемента.
Runtime передаёт Rigidbody суммарную силу в COM и суммарный момент, что эквивалентно
сумме сил в соответствующих точках. Второй момент от той же силы не добавляется.
При отсутствии ветра мощность аэродинамического wrench `F·vCOM + torque·omega <= 0`.
Ветер может передавать энергию корпусу; диссипацию проверять относительно воздуха.

Поверхности требуют уникальные surfaceId, единичные normalLocal, areaM2>0 и Cd>=0;
допускается 1–256 элементов. Нормальная pressure-модель — наше выбранное приближение
для участков, не измеренная модель конкретного дрона. `dragCoefficient` необходимо задавать
вместе с принятой площадью. Общая основа квадратичного drag:
[NASA Glenn: Drag Equation](https://www1.grc.nasa.gov/beginners-guide-to-aeronautics/drag-equation/).

## Проверки и нестабильные тесты прошлого этапа

Пользователь подтвердил ручной полёт, EditMode и успешный повторный запуск всех PlayMode
тестов этапа 2. Первые запуски hover/yaw были нестабильны. Значение ~0.09698 m/s у hover
соответствует примерно одному шагу свободного падения 0.01 s, с последующим слабым drag.
Старая SetUp создавала активный Rigidbody до настройки профиля; yaw также мог получить
disarm при переключении фокуса. Это обоснованные гипотезы, не воспроизведённый здесь диагноз.

Теперь Rigidbody/pilot тесты создают неактивный объект в отдельной LocalPhysicsMode.Physics3D
сцене, явно инициализируют компоненты и выполняют одинаковые шаги control → forces → Simulate.
Ни глобальный timestep, ни физика Terrain, ни фокус редактора не управляют этим стендом.
Тестовые пороги не ослаблены. В обычной сцене сохраняются FixedUpdate и disarm при потере фокуса.
Документация Unity о явном шаге: [PhysicsScene.Simulate](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/PhysicsScene.Simulate.html).

78 тестов ядра прошли, включая 31 новый: sphere/box, масштаб, перекрытия, LUT, энергия,
вращательная скорость CP, момент давления и валидация. Добавлены три Unity-проверки:
wind → ProjectedArea force, торможение yaw поверхностями, преобразования импортированного mesh.
Все 15 PlayMode случаев и редакторский экспорт этапа 3 требуют запуска у пользователя:
здесь Unity отсутствует. Прохождение ядра не подтверждает импорт/работу меню редактора.
