# Этап 4: характеристики винтов

Геометрия корпуса запекается в редакторе. RPM-таблицы и карты винтов также разбираются,
сортируются и копируются в private runtime-массивы один раз при Initialize. В каждом шаге
выполняются поиск интервала и интерполяция; mesh и CSV в полёте не обрабатываются.

## Что реализовано

| Модель | Расчёт | Плотность / обтекание |
|---|---|---|
| OmegaSquared | T=kT ω²; Q=kQ ω² | Только referenceAirDensityKgM3; осевой поток не меняет коэффициенты |
| CtCq | T=Ct ρ n² D⁴; Q=Cq ρ n² D⁵ | Текущая плотность; постоянные Ct/Cq |
| RpmTable | Линейная интерполяция измеренных thrustN, torqueNm, optional currentA по RPM | Только referenceAirDensityKgM3; статическая таблица не моделирует обтекание |
| PerformanceMap | Интерполяция Ct/Cq по RPM и J, затем формулы Ct/Cq | Текущая плотность; осевой поток в точке ротора |

n=RPM/60, ω=2πn. Q — момент на винте; на корпус действует spin-dependent реакция:
CW → -Q axis, CCW → +Q axis. Каждый ротор выбирает ровно одну performance-модель;
таблица/карта **заменяет** kT/kQ, а не умножает их. Ct/Cq дополнительно не масштабируются
по reference density. Cp не равен Cq: при этих соглашениях Cq=Cp/(2π).

Для карты `J=Vaxial/(n D)`, `Vaxial=dot(VrotorPoint-Vwind, thrustAxisWorld)`.
Положительный J соответствует движению аппарата вдоль положительной оси тяги относительно
воздуха. Скорость точки включает ωbody × (rRotor-rCOM). Поперечная составляющая не
входит в J. Нет добавочного induced-velocity/translational-lift множителя поверх карты.
Висение использует J=0; отрицательный J требует своих данных или явно выбранного Clamp.
Карта не подтверждает точность vortex ring state, бокового потока и взаимодействия роторов.

Основа соглашений: [UIUC, Deters/Ananda/Selig 2014](https://m-selig.ae.illinois.edu/pubs/DetersAnandaSelig-2014-AIAA-2014-2151.pdf),
раздел Data Reduction (T, P, J); [UIUC Propeller Database Vol. 2](https://m-selig.ae.illinois.edu/props/volume-2/propDB-volume-2.html).
Наши fixtures синтетические; они не являются измерениями UIUC или характеристиками FPV-дрона.

## Таблицы и диапазоны

RpmTable: 2–4096 строк, уникальные RPM; порядок JSON произвольный, runtime сортирует.
Все силы, моменты и токи неотрицательны. Нужна явная точка RPM=0, T=0, Q=0 и I=0,
если ток задан. Эта точка обеспечивает остановку без остаточной тяги и непрерывный старт.
Не добавляем её молча при импорте. currentA либо есть у всех строк, либо отсутствует у всех.
Отсутствие тока сохраняется как null в C#; это не измеренный нулевой ток.
Ток хранится/интерполируется для телеметрии, но пока не расходует батарею и не ограничивает мотор.

PerformanceMap: до 4096 ячеек, полный прямоугольный RPM × J grid без дублей, минимум
один положительный RPM и два значения J. В каждой RPM-строке одинаковые значения J.
Обязательна колонка J=0 для статического запаса тяги и тестового пульта. Между узлами —
билинейная интерполяция коэффициентов; при единственной RPM-строке меняется только J.
Разреженные/нерегулярные данные перед импортом нужно привести к общей сетке явно.
Опциональный Reynolds сохраняется как метаданные, отдельного измерения интерполяции по Re нет.
Отрицательные Ct/Cq сохраняются и дают знаковые силы/моменты; runtime не исправляет такие
данные нулём. Электрическая модель windmilling/рекуперации ещё не реализована.

`outOfRangePolicy` обязателен для таблиц/карт:

| Политика | RpmTable | PerformanceMap |
|---|---|---|
| Clamp | За границами держит крайние T/Q/I | Ограничивает координаты lookup RPM/J; физические n² и J считаются по фактическим RPM |
| Reject | Отклоняет запрос за границей таблицы | Отклоняет RPM или J за границей карты |

Это разные физические соглашения. Clamp не экстраполирует линейный наклон Ct/Cq.
У карты ниже первого положительного RPM используются крайние коэффициенты, поэтому
при раскрутке сила стремится к нулю как RPM². При RPM=0 любой режим возвращает T=Q=0
до вычисления J (без деления на ноль); stationary propeller drag здесь не моделируется.

Reject должен покрывать motor.maxRpm при загрузке. Положительные промежуточные RPM
ниже первой строки карты при motor lag всё равно выходят за её диапазон; loader выдаёт
предупреждение, тестовый пульт такую карту не принимает. Для обычного старта выбирать Clamp.
При runtime Reject DronePhysicsBody отвергает **весь шаг до приложения сил**, disarm,
выдаёт ошибку и отключает модуль. Остановить Play и исправить профиль; это ошибка данных,
а не физическая модель полёта за пределами измерений. CLAMP виден в HUD каждого ротора.

## Пульт и ограничения

Для RpmTable пульт инвертирует таблицу T(RPM). Для PerformanceMap инвертируется статическая
кривая J=0. Если статические Ct/Cq постоянны, используется аналитический sqrt путь.
Для нелинейных кривых геометрия задаёт collective/roll/pitch, оставшаяся степень свободы
решает yaw по фактическому Q(T). Насыщение масштабирует запрошенные оси torque вместе,
сохраняя достижимый collective. Статическая вместимость консервативна для разных роторов.

Пульт требует 4 оси +Y, управляемую геометрию, положительную строго растущую статическую
тягу, неотрицательный неубывающий статический Q и положительный Q на максимуме.
Для нелинейного allocator нужна монотонная yaw null-space и minRpm=0 у всех роторов.
Валидный физический профиль может не подходить этому тестовому пульту; импорт сообщает это.

**Физика карты использует текущее обтекание, allocator пульта — номинальное J=0.**
PID компенсирует отклонение, пока есть запас, но запрошенный wrench при ненулевом J
не обещает точного совпадения. Flow-aware controller allocation — отдельное улучшение;
не менять физические коэффициенты ради его компенсации. MaxTotalThrust/T/W — статический
запас при J=0, не гарантированная тяга во всех режимах движения.

## Проверка в Unity

1. Подтянуть ветку physics-packages; дождаться компиляции.
2. Window → General → Test Runner → EditMode → Run All; затем PlayMode → Run All.
3. Для чистого стенда назначить DronePhysicsBody → Drone Profile:
   `Assets/DronePhysics/Resources/DronePhysics/quad_test_rpm_table.json`.
4. Play → F → H. Проверить удержание высоты, Q/E, затем H выключить и отпустить Space.
   При точных 5000 RPM один ротор даёт 2.4525 N; таблица между узлами линейна,
   поэтому произвольные RPM отличаются от исходной модели RPM².
5. Повторить с `quad_test_performance_map.json`: статическая тяга совпадает с Basic,
   набор/снижение высоты меняет J; CLAMP при малых RPM во время старта ожидаем.

Пресеты имеют тестовую геометрию. Чтобы оставить свою модель/маркеры, использовать импорт:

1. Выбрать свой корень с DronePhysicsBody; выйти из Play.
2. DroneLab → Propellers → Import Performance CSV.
3. В CSV asset перетащить `Assets/DronePhysics/Examples/propeller_rpm_table.csv`
   или `propeller_performance_map.csv`.
4. Выбрать соответствующий Model; Out of range = Clamp. Для RPM-таблицы Reference density
   равна Environment density (Calm = 1.225). Apply to all rotors = включено для одинаковых роторов.
5. Validate and save new drone JSON → выбрать **новое** имя, например `drone_mesh_rpm.json`.
6. Новый JSON назначится корню; сохранить сцену. Геометрия, масса, motor.maxRpm и времена
   отклика сохраняются. Изменяются выбранные performance и provenance; derived удаляется.
7. Play → F → H и проверить полёт. Вернуть исходный JSON можно через Inspector.

CSV имеет запятую как разделитель, точку в десятичной части, SI и точные заголовки:

```csv
rpm,thrustN,torqueNm,currentA
0,0,0,0
2500,0.613125,0.0122625,1
5000,2.4525,0.04905,3
7500,5.518125,0.121,7
10000,9.81,0.25,12
```

```csv
rpm,advanceRatio,ct,cq
5000,0,0.1,0.01
5000,0.5,0.07,0.0085
10000,0,0.1,0.01
10000,0.5,0.07,0.0085
```

Порядок колонок может меняться. Неизвестные колонки, Cp вместо Cq, пропуски, NaN,
Infinity, неверная сетка и дубли отклоняются. Числа с десятичной запятой не угадываются.
Импортированные данные отмечаются User: название CSV само по себе не доказывает измерение.
Реальную массу, COM/инерцию и экспериментальные характеристики настроим отдельно.
