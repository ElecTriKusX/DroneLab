# Разработка и доработка форка

[Документация](README.md) · [Архитектура](ARCHITECTURE.md) · [Проверки](TESTING.md)

## Окружение

| Компонент | Назначение |
|---|---|
| Unity 6000.3.25f1 | Импорт, интерфейс, сцены, Play Mode и Player |
| HDRP 17.3.0 | Текущий графический конвейер; версия закреплена в `Packages/manifest.json` |
| Git | Клонирование, история исходников и получение Git-зависимостей UPM |
| .NET SDK 8 | Тесты чистого C# и утилита численной валидации |
| Python 3.11 | Версия CI для генераторов, упаковки и регрессионных тестов |

UPM-зависимости устанавливаются из `Packages/manifest.json`. Локальный пакет конфигуратора находится в `Distribution/Packages/com.dronelab.configurator`; не исключайте `Distribution` при клонировании. Первый импорт glTFast требует доступа к его Git-источнику.

Некоторые дополнительные сцены и визуальные ресурсы могут передаваться отдельно. Отсутствующие ассеты нужно восстановить из комплекта команды или убрать зависимость в собственной сцене; документация не включает эти файлы.

## Создать форк

Создайте Fork на GitHub и клонируйте свою копию. В командах замените `YOUR_ACCOUNT` на имя аккаунта.

```bash
git clone https://github.com/YOUR_ACCOUNT/DroneLab.git
cd DroneLab
git remote add upstream https://github.com/ElecTriKusX/DroneLab.git
git switch -c feature/my-change
```

Откройте проект в Unity нужной версии и убедитесь, что `MainMenu` запускается до внесения изменений. Для получения обновлений исходного проекта:

```bash
git fetch upstream
git switch main
git merge upstream/main
git switch feature/my-change
git merge main
```

Разрешайте конфликты в исходниках, затем пересоздавайте производные файлы штатными генераторами. Не редактируйте `Library/PackageCache`: его содержимое Unity может восстановить заново.

## Где вносить изменения

| Область | Путь |
|---|---|
| Математическая физика и контракт | `Assets/DronePhysics/Core` |
| Связь физики с Rigidbody | `Assets/DronePhysics/Unity` |
| Пилот и ввод | `Assets/DronePhysics/Demo/Runtime` |
| Дискретные модели оборудования | `Assets/DroneSensors/Core` |
| Интерфейс и интеграция приложения | `Assets/DroneUI/Runtime` |
| Каталоги и встроенные профили UI | `Assets/DroneUI/Resources/DroneLab` |
| Среда и адаптеры | `Assets/DroneEnvironment/Core`, `Runtime`, `Editor` |
| Экспортируемые UPM-пакеты | `Distribution/Packages` |
| Генераторы и анализ | `Tools` |
| Автоматические проверки | `Tests`, тестовые каталоги в `Assets` |

Главные правила разделения: чистое ядро не зависит от Unity; UI не прикладывает физические силы; один `Rigidbody` не получает одновременно старый и новый набор силовых модулей. Подробности — в [архитектуре](ARCHITECTURE.md).

## Типовые задачи

### Добавить аппарат

Для собственного дрона используйте [конфигуратор](UI/DRONE_CONFIGURATOR.md) и экспортируйте сохранённый комплект. Для встроенного образца подготовьте каталог с `document.json`, `profile.json`, моделью и привязками; утилита `Tools/install_builtin_drones.py` устанавливает такие комплекты в ресурсы проекта. Перед использованием утилиты посмотрите её `--help`.

Наличие визуальной модели не подтверждает физические параметры. Укажите происхождение характеристик, проверяйте единицы, плотность измерений, COM, инерцию и запас тяги. Проверка полёта проводится для пары «дрон + среда».

### Добавить сцену или погодный профиль

Подготовьте colliders и стартовую площадку, добавьте `DroneSpawnPoint`, зарегистрируйте сцену в `ScenarioCatalog` и активном Build Profile. Полная процедура: [интеграция запуска](UI/SIMULATION_LAUNCH.md). Настройка параметров среды: [сценарии и окружение](UI/SCENARIOS_AND_ENVIRONMENT.md).

### Изменить физику или JSON-контракт

Читайте [руководство физического SDK](Physics/DEVELOPMENT.md). Источник контракта — `Tools/generate_physics_contract.py`. DTO, схемы и `PARAMETERS.md` пересоздаются вместе; единицы и имена действующих полей нельзя менять незаметно для существующих профилей.

При изменении полей также обновите каталог подсказок конфигуратора:

```bash
python Tools/generate_physics_contract.py
python Tools/generate_configurator_catalog.py
```

### Изменить UI или датчик

UI Toolkit отвечает за экраны, а дискретная модель датчика — за измерения. Сохраняйте явный фокус полей F3/F4 и различие между временем захвата и доставки. Для нового канала обновите модель, адаптер, отображение, запись и проверки. Контуры ориентации и высоты сейчас читают физическое состояние; перевод на оцениватель состояния требует отдельной реализации.

## Исходники и экспорт пакетов

В этом Unity-проекте физика используется из `Assets`. Экспортированные Physics/Demo/Environment предназначены для подключения в другом проекте. Не подключайте их поверх тех же исходников в `Assets`: это создаёт дубли классов и сборок.

После изменений исходных файлов или документации пересоздайте экспорты:

```bash
python Tools/build_unity_packages.py
python Tools/build_environment_package.py
python Tools/build_unity_packages.py --check
python Tools/build_environment_package.py --check
```

Вместе с копиями файлов обновляются их SHA-256. Исправление только MD в `Documentation~` оставляет экспорт несогласованным; правьте документ-источник и запускайте генератор.

## Проверка и Pull Request

Выполните проверки из [TESTING.md](TESTING.md), затем проведите ручную проверку изменённых экранов или поведения в Unity. В PR укажите проблему, получившееся поведение и реальные результаты проверки. При добавлении Unity-ресурсов сохраняйте `.meta` с исходными GUID.

Текущий workflow `.github/workflows/physics-packages.yml` запускается автоматически для веток `physics-packages`, `physics-plugins`, `envieroment-packages` и поддерживает `workflow_dispatch`. Для собственного процесса с PR в `main` измените фильтры веток в форке или запустите workflow вручную. Наличие workflow в репозитории само по себе не означает запуск на каждом PR в `main`.

## Сборка приложения

1. В Unity откройте **File → Build Profiles**, выберите Windows и установите нужный Build Support.
2. Проверьте список сцен: `MainMenu` должен быть стартовой сценой, выбранные игровые сцены — входить в сборку.
3. Соберите Player в отдельный каталог.
4. Проверьте запуск на целевом компьютере, импорт модели, материалы, меню, F1–F5 и запись CSV.
5. Упакуйте весь каталог Player в ZIP, сохраняя EXE, данные и библиотеки вместе.

Для публикации прикрепите ZIP к GitHub Release. Кроссплатформенная сборка приложения пока относится к [roadmap](ROADMAP.md); проверки чистого C# на двух ОС не заменяют проверку Player.
