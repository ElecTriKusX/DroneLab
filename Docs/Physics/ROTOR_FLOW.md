# Роторный поток — этап 10

Лёгкая эмпирическая модель для статических характеристик винта. Она расширяет
rotor H-force и ground effect, не требует mesh/CFD в runtime. Это не VRS, BEMT,
динамический wake или геометрическая деформация лопастей.

## Формулы и источник

Скорость каждого ротора: `v = Vcom + omegaBody × (rRotor-rCOM) - wind(rRotor,t)`.
Ось `a` берётся из активного JSON и преобразуется в world space. `u=dot(v,a)`,
`vperp=v-u*a`, `omega` — фактические ограниченные батареей rad/s.

Базовые зависимости соответствуют RotorPy:

- осевая поправка: `dT_axial = -kz * omega * u`;
- translational lift: `dT_lift = kh * dot(vperp,vperp)`;
- продольный flapping moment: `Mflap = -kf * omega * cross(v,a)`.

Первичный источник линейных силы/момента — Folk, Paulos, Kumar, RotorPy (2023),
раздел II-B, уравнения (8–9):
https://imrclab.github.io/workshop-uav-sims-icra2023/papers/RS4UAVs_paper_3.pdf.
Квадратичный lift — `compute_body_wrench` в реализации RotorPy, commit
`40b09697a6a1596d404a67f459941d46a39eedd3`, проверен 2026-10-05:
https://github.com/spencerfolk/rotorpy/blob/40b09697a6a1596d404a67f459941d46a39eedd3/rotorpy/vehicles/multirotor.py.
Наши ограничения, stop gating, произвольные оси и scaling плотности — явные дополнения,
не результаты независимой аппаратной калибровки RotorPy или нашего аппарата.

`inducedDrag` — историческое имя флага; здесь оно означает **линейную поправку осевого
inflow**, а не дополнительное боковое сопротивление. Положительная скорость вдоль
оси снижает тягу, отрицательная повышает в пределах ограничителя. Это нельзя
экстраполировать на глубокое снижение/VRS. Flapping не зависит от CW/CCW в данной
упрощённой продольной модели. Для +Y ротора и потока +Z момент +X наклоняет нос вниз.
Реактивный момент вращения винта остаётся отдельным `ReactionSign*Q*axis`.

## Параметры, включение и ограничения

Все поля находятся в `rotors[].advancedAerodynamics`. Старый H-force
`rotorDragCoefficientKgPerRad` сохраняет прежний смысл и не масштабируется по rho.

| Поле | Единицы / действие |
|---|---|
| `bladeFlappingCoefficient` | kg·m/rad; включается флагом `bladeFlapping` |
| `inducedDragCoefficient` | kg/rad; включается флагом `inducedDrag` |
| `translationalLiftCoefficientKgPerM` | kg/m = N/(m/s)²; положительное значение + `rotorAerodynamics` включает lift |
| `referenceAirDensityKgM3` | kg/m³, ≥1e-6 для численной устойчивости; коэффициенты **трёх новых** поправок умножаются на `rho/referenceRho` один раз |
| `maxAirSpeedMps` | m/s, >0…200; локальная скорость для новых поправок ограничивается по модулю с сохранением направления |
| `maxThrustCorrectionFraction` | 0…0.5; ограничение суммарной `dT_axial+dT_lift` относительно положительной базовой тяги |
| `maxFlappingMomentRatio` | 0…1; максимум `|Mflap|/(Tbase*R)` |

Reference rho и speed envelope требуются при включении любого нового эффекта;
коэффициент и соответствующий ограничитель задаются явно, пропуск — ошибка.
Предел 200 m/s — проверка численного ввода, а не универсальная область точности.
В тестовом профиле envelope=15 m/s, thrust fraction=.25, moment ratio=.2.
Это **синтетические оценки**, не рекомендуемый пресет конкретного FPV-дрона.

Поправка общей тяги: `dT=clamp(dT_axial+dT_lift,-fraction*Tbase,+fraction*Tbase)`.
Модуль момента ограничивается `ratio*Tbase*R`, направление сохраняется.
При `omega=0` или `Tbase<=0` новые поправки равны нулю. При малых RPM ограничения
по Tbase гарантируют непрерывное исчезновение lift/moment вместо подъёма остановленного
винта. При отсутствии новых флагов/коэффициентов старые профили ведут себя как прежде.
Clipping публикуется отдельно от clipping таблицы; это ограничение модели, не физическое
доказательство насыщения аэродинамики. Пользователь должен видеть выход из envelope.

Ground effect применяется после новой поправки: `Tfinal=(Tbase+dT)*GE` для положительной
тяги. Исправленная тяга и старый H-force прикладываются в rotor point **один раз**;
`AddForceAtPosition` сам создаёт r×F. Mflap прикладывается отдельным AddTorque и не
повторяет r×F. Переворот axis в JSON меняет все проекции; Scene markers сами JSON не меняют.

## Совместимость и энергия

OmegaSquared/CtCq/RpmTable допускаются при статических free-air исходных кривых.
RPM/J PerformanceMap уже описывает осевой поток: `inducedDrag` с ней отклоняется.
Наш lift bundle с PerformanceMap тоже отклоняется до согласования моделей/энергетики.
Чистый flapping moment можно использовать с картой без дублирования её осевой тяги.
Не включать H-force/flapping/lift поверх данных, где тот же эффект уже включён в fitting.
Вращающиеся винты следует исключить из аэродинамической модели неподвижного корпуса.

Q и измеренный ток остаются на исходных характеристиках. Батарея считает Q*omega и
электрические потери, как прежде; **новая тяга не превращается автоматически в
дополнительную электрическую мощность**. Сопротивление/изменение эффективности и
момент могут обмениваться энергией с воздухом и приводом, но совместный load solver,
вращательная энергия и полная энергетическая согласованность не реализованы этапом 10.
Ограниченные поправки полезны для поведения в потоке, но это не энергетическая модель
для точного предсказания дальности/времени полёта. Следующее расширение — этап 11.

JSON остаётся 1.0.0: добавлены только необязательные поля и реализованы прежде
зарезервированные флаги; единицы старых работающих полей не изменены. Новые профили
нуждаются в runtime/schema этапа 10. CSV имеет отдельную версию 1.1.0: добавлены
`thrust_correction_n` (до GE), `flap_x/y/z_nm` (world) и `flow_clamped` для каждого ротора.
`thrust_n` уже содержит dT и GE; нельзя прибавлять их к нему повторно.
Python-анализатор читает столбцы по именам, поддерживает старые и новые записи.

## Проверка в Unity

1. Обновить ветку `codex/physics-foundation`, открыть проект, запустить EditMode/PlayMode.
2. Выбрать Terrain → **DroneLab → Diagnostics → Create Advanced Rotor Acceptance Drone**.
3. Назначить новую цель DroneTestCamera, сохранить сцену. Включить Play, F, H.
4. HUD показывает `Rotor flow dT`, `flap moment`, `flow limit`. При боковом полёте
   поправки меняются; в спокойном неподвижном воздухе равны нулю. Ветер общего стенда
   включён, поэтому одного нулевого world velocity недостаточно для нулевого потока.
5. Проверить набор/снижение и ручной Fault. CSV записывает новые эффекты каждого шага.

На своём дроне: **DroneLab → Rotors → Create Profile with Rotor Effects**. Новые toggles
по умолчанию выключены; настройки явно включаются, новый JSON валидируется и назначается.
Physics не использует тяжёлый анализ геометрии во время полёта.

Изолированные PlayMode сценарии проверяют нулевые поправки в calm hover, боковые
lift/flapping, осевой знак, применение hub/lever моментов один раз, stop/fault/reset
и совместный pilot+wind+atmosphere+battery сценарий. Pure tests дополнительно проверяют
константы, arbitrary axes, snapshot, rho, запреты моделей и 50/100/200 Hz. Unity нужен
для проверки фактического Rigidbody, а не только математического ядра.

UPM snapshots в Distribution пока остаются на этапе 9/0.2.0: по решению пользователя
пакеты пересобираем после завершения улучшений. Сейчас тестировать Assets/DronePhysics.
