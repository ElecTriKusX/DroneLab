## Сверка физических величин с исследованием

| Величина / модель исследования | Фактическая реализация | Статус / существенная оговорка |
|---|---|---|
| Размеры, масштаб и оси | `coordinateSystem`, `massProperties.dimensionsM`; physics root scale 1 | Есть; 1 Unity unit = 1 m в физическом корне |
| Масса и COM | `massKg`, `centerOfMassLocalM` | Есть; задаются пользователем, не вычисляются из внешней формы |
| Полный тензор инерции | `ManualPrincipal`: три главных момента + `principalAxesRotationXyzw`; `AutoBox` fallback | Представление общего SPD-тензора есть; импорт 3×3/eigen decomposition и сборка из масс по Штейнеру отсутствуют |
| Геометрия collision | Unity colliders, тестовый BoxCollider | Есть; collision mesh и aero mesh — разные назначения |
| Положение, ось и CW/CCW ротора | `rotors[].geometry` | Есть; силы используют JSON snapshot, а не scene markers |
| Минимальные/максимальные/idle RPM | `rotors[].motor`; внутри rad/s | Есть |
| D / pitch / blade count | `propeller` | D участвует в Ct/Cq и ground effect; pitch/count идентифицируют винт, сами не определяют T/Q |
| T=kω², Q=kω² | `performance.model=OmegaSquared` | Есть; привязка к reference density, не универсальная поправка плотности |
| CT/CQ с D и ρ | `CtCq` | Есть; постоянные коэффициенты требуют калибровки |
| Таблицы T/Q/RPM | `RpmTable` + CSV | Есть; измеренная плотность фиксирована, currentA — табличная телеметрия |
| CT/CQ(RPM,J) | `PerformanceMap`, локальная осевая скорость точки ротора | Есть; allocator использует статическое J=0, батарея с этой картой явно отклоняется |
| KV, Rm, I0, motor/ESC I/P limits | `motor.electrical` | Есть, квазистационарный Electrical governor |
| Lm, Jr, отдельная задержка ESC | Не решаются | Нет; exponential motor lag не заменяет электрическую/механическую ODE |
| τ мотора | `responseTimeUpS`, `responseTimeDownS` | Есть, разные времена разгона/замедления |
| КПД мотора/ESC | Константы; в Electrical потери back-EMF/copper и ESC, без повторного motor efficiency | Частично; кривых КПД нет |
| Battery capacity/OCV/R/SOC | `powerSystem.battery` | Есть; нет температурной зависимости, старения и регенерации |
| Cd и опорные площади | `AxisApproximation`, `ProjectedArea` с box/LUT | Есть; silhouette определяет площадь, но не Cd |
| CP и aero parts | `dragApplicationPointLocalM`, `Surfaces` с отдельными потоками | Есть; Surfaces — двусторонние pressure patches, без lift polar и экранирования |
| Rotor H-force | `rotorDragCoefficientKgPerRad`, F=−KωVperp | Есть; empirical, без самостоятельной поправки плотности |
| Translational lift | Дополнительная модель не реализована | Нет; RPM/J карта осевого потока не заменяет боковой inflow-механизм |
| Axial induced drag / dynamic inflow | Отдельной силы/состояния нет | Нет; hover induced-speed estimate предназначен для VFX, не влияет на физику |
| Blade flapping | Зарезервированный module flag | Нет; включение отклоняется, не скрытый no-op |
| Ground effect | Ограниченный empirical множитель T, высота и нормаль локального collider | Есть; Q не усиливается, нет полноценной модели wake near terrain |
| Rotor gyroscopic moment | Зарезервированный module flag | Нет; не путать с вращательной динамикой Rigidbody |
| Gravity и air density | `gravityMps2`, Constant/StandardAtmosphere | Есть; единая ρ для CtCq и Qω энергетики |
| T/P/altitude воздуха | Сухая тропосфера, −500…11000 m, world-height anchor | Есть в пределах модели; не произвольный прогноз погоды |
| Mean wind и gust | World velocity, raised-cosine overlay | Есть; направление порыва вдоль mean wind, при нуле +X |
| Turbulence σ/τ/seed | Bounded Fourier field, peak intensity / timescale / seed | Частично: intensity не RMS σ, timescale не Dryden correlation τ |
| Пространственный ветер | `IWindProvider` + отдельные samples роторов/CP/patches | Есть; застройка сама не создаёт аэродинамическое поле |
| Отказы | Авторитет привода 0…1, coast-down, отключение питания отказавшего ротора | Есть; не повреждение лопасти, разрушение или recovery controller |
| Независимая валидация | Аналитические тесты, dt comparisons, CSV и процедуры калибровки | Инструменты есть; ground-truth bench/flight comparison пока нет |

Нельзя включить все варианты одновременно: Box/LUT/Surfaces — альтернативы;
OmegaSquared/CtCq/RpmTable/PerformanceMap — альтернативы; переменная атмосфера
несовместима с фиксированными измеренными данными без модели поправки; battery+RPM/J
пока запрещены. [Финальная проверка](FINAL_ACCEPTANCE.md) покрывает общий совместимый
профиль и альтернативные ветви отдельно.

## Какую точность можно заявлять

Сейчас это параметрическая полуэмпирическая 6DoF-модель с проверенной математикой
ядра и подтверждённым пользователем поведением Unity-стенда. Она пригодна для
демонстрации качественных последствий массы, геометрии, тяги, ветра, заряда и отказов.
Высокую точность относительно конкретного FPV-дрона пока заявлять нельзя.

Скачанная визуальная модель улучшает форму/силуэт после экспорта. Она не сообщает
реальную массу, COM, инерцию, Cd, стендовые характеристики мотора/винта или PID
настоящего аппарата. Все `quad_test_*` остаются синтетическими. В частности,
CT/CQ финального 1 kg / 5 inch стенда специально согласованы с прежней тестовой
тягой, а не являются рекомендуемыми коэффициентами настоящего 5-inch винта.

Для подтверждения точности нужны: известная сборка; измеренные масса/COM/I;
T/Q/I/RPM при нескольких напряжениях и режимах; motor step; проверка сопротивления;
отдельные реальные логи зависания, разгона, yaw, снижения и работы батареи.
Один набор используется для fitting, другой — для проверки. Отчёт должен содержать
RMSE, диапазон RPM/скорости/напряжения и условия. До этого никакой «точности 95%».
Даже RotorPy описывает benchmark testing against real data, а не ограничивается
внутренними тестами формул: https://arxiv.org/abs/2306.04485.
Возможный источник propeller bench curves: https://m-selig.ae.illinois.edu/props/propDB.html;
использовать данные именно соответствующего винта и условий, не случайные похожие.

Для быстрого/агрессивного FPV следующим физическим расширением полезны validated
translational lift + axial inflow + flapping. Для предсказания глубокого вертикального
снижения отдельно нужна модель vortex ring state. Сейчас VRS, rotor wake interaction,
CFD и полноценная динамическая аэроупругость не реализованы.

Отказ одного двигателя обычного quad приводит к потере доступного управления;
текущий пульт не является специальным трёхмоторным recovery controller. Это ожидаемый
результат стенда. Но наклон при снижении с исправными моторами сам по себе не доказывает
VRS: возможны команды/режим PID, насыщение, асимметрия COM/тяги, ветер, контакт и нехватка
питания. Для диагностики нужен CSV с mode/command/torque/RPM/power limits, а не только
изображение. В полученном коммите пользователя `2d5d96d` сцена
`Assets/Scenes/PhysTest.unity` использует `drone_battery.json` и `environment_calm`,
но имеет `DroneMotorFaultScenario.automaticFault=true`, rotorIndex=0, secondsAfterArm=5.
Перед опытом с исправными моторами нужно отключить Automatic Fault и сбросить состояние.
Это наблюдение о сохранённой сцене, а не доказательство причины уже увиденного падения.
Отдельный новый тест проверяет симметричное снижение без выдуманного
опрокидывающего момента.

## Сверка с ТЗ соревнования

Оценка касается физического модуля, а не результата параллельной команды карты/UI.
Мультиротор выбран в разрешённой ТЗ категории; самолётная физика не обязательна.

| Требование ТЗ | Состояние физического модуля / передача команде |
|---|---|
| Параметризованный профиль, загрузка через конфигурацию | JSON/schema/validator готовы; runtime file picker, безопасное применение профиля и меню — интеграция UI |
| Real-time динамика, тяга, сопротивление, гравитация | Реализовано; численная проверка есть, аппаратная калибровка впереди |
| Ветер и турбулентность | Реализовано; UI задаёт скорость/направление/seed |
| Температура воздуха | Участвует в atmosphere; воздействие температуры на мотор/батарею не реализовано |
| Дождь, снег, град | Не реализованы в физическом модуле; нужны погодные presets/VFX и явная документированная модель воздействия, если оно заявляется |
| GPS, IMU accel/gyro/magnetometer, барометр, дальномер, камера | Отдельных моделей датчиков нет. Чтение Rigidbody/physics state — идеальная телеметрия, не модель датчиков |
| Altitude/speed/attitude/SOC | Runtime/CSV готовы для HUD |
| Engine temperature и signal level | Отсутствуют; нельзя подставить произвольные числа и назвать физикой |
| Autopilot* | Angle/Acro + H; позиционный/маршрутный режим отсутствует |
| Export report* | CSV+manifest, анализатор есть; пользовательский экран графиков/отчёта — интеграция |
| Third-person/FPV/free view, карта/terrain selection, menu/HUD | Часть стенда камеры есть; полноту пользовательских экранов проверяет команда |
| Aero/sensor VFX* | Force gizmos и rotor telemetry API есть; итоговые эффекты/зоны сенсоров не реализованы |
| EXE, публичный repo, видео, презентация | Финальная сборка и материалы команды, не доказаны unit-тестами |

В ТЗ sensor models, погода, engine temperature и signal level не помечены звёздочкой.
Autopilot/расширенная визуализация/экспорт помечены. Поэтому до дедлайна 10.10.26
приоритет: собрать рабочий EXE с общей UI/картой, закрыть обязательные sensor/weather
пункты упрощёнными честно описанными моделями и провести сквозную приёмку.

Следующий полезный слой: отдельные sensor DTO/API с ideal/noisy modes, частотой,
задержкой и seed; GPS из world origin, gyro из ω, accelerometer specific force,
magnetometer из заданного поля, barometer из atmosphere, rangefinder raycast,
упрощённая камера/FOV. Не подключать шум к существующим PID автоматически:
сначала датчики/HUD, затем отдельная оценка состояния и сенсорный controller.
Engine thermal и radio link также требуют отдельных моделей и единиц.

## Маркеры и JSON

Маркеры — authoring, не движущиеся runtime роторы. Физика использует активный JSON,
который загружается в snapshot при Initialize. Перемещение/поворот маркера не меняет
snapshot, даже если выбран battery profile. Это относится к любому профилю.

1. Stop Play → выделить корень дрона → проверить нужный `Drone Profile`.
2. При необходимости `DroneLab → Geometry → Create Markers from Profile`.
3. Изменить Rotor/COM/Drag Point. Стрелка local +Y задаёт тягу.
4. `DroneLab → Geometry → Export Profile with Marker Geometry Only` → сохранить
   новый JSON. Он назначается в DronePhysicsBody автоматически.
5. Сохранить сцену → Play. Этот экспорт сохраняет aero mode/tables, engine/propeller
   характеристики, battery и module flags; обновляет rotor geometry, COM и CP.
   Mesh silhouette или поверхности этим экспортом не пересчитываются; для их изменения
   использовать соответствующий Box/Mesh/Surfaces экспорт.

Поворот на 180° вокруг Y не переворачивает ось +Y; вокруг X/Z — переворачивает.
Изменение CW/CCW меняет знак reaction torque, не направление тяги.
Перевёрнутые оси допустимы физическому ядру, но DroneTestPilot рассчитан на четыре
параллельные +Y оси и отклонит этот layout. Для теста направленной вниз тяги нужен
прямой моторный command, а не обычный quad pilot. Это проверяется новым PlayMode-тестом.

## Маршрут в готовом приложении: предложение следующего этапа

Unity пользователю не нужен. Предлагаемый MVP — кнопка «Маршрут» в FreeCam:
клик raycast в Terrain/разрешённый collider добавляет точку над выбранным местом;
рядом задаётся высота над землёй (например 5 m), скорость и время остановки.
Точки и соединяющая линия отображаются в мире; точки можно удалить/перетащить,
есть undo, Start/Pause/Resume/Cancel и Save/Load JSON. При неудачном raycast точка
не добавляется. Клики по UI не проходят в мир. Для воздушных точек позже можно
добавить плоскость заданной высоты и вертикальный gizmo.

Клик выбирает место на карте, а не altitude=0. Высоту нужно определить явно.
Для MVP: разовая выборка поверхности + heightAboveGround даёт world Y точки.
Это не постоянное terrain following между точками и не obstacle avoidance.
Маршрут по прямым отрезкам может пересечь холм/здание; нужен preview, проверка
отрезков/clearance либо видимое предупреждение. Безопасность нельзя обещать по
одним waypoint'ам. Предпочтителен ограниченный открытый полигон первой демонстрации.

Формат маршрута — отдельный versioned JSON: mapId/mapVersion/world origin,
метры и Unity Y-up frame, waypoints `{positionWorldM, speedMps, acceptanceRadiusM,
waitS, yawDeg?}`, maxSpeed/maxAcceleration. Scene-specific маршрут валидируется
при загрузке; сохранение в доступную runtime папку. DroneProfile не хранит путь.

Полёт: planner ограничивает скорость/ускорение → внешний position/velocity PID
формирует желаемые ускорение/наклон/collective → существующий attitude/rate/motor
контур. Не перемещать Rigidbody через Transform/MoveTowards: тогда проверка массы,
ветра и батареи потеряет смысл. Нужен общий command API с явным mode arbitration,
не имитация клавиатуры. H отдельно не способен облететь точки, поскольку не держит X/Z.
Manual override немедленно отменяет route; fault/low battery/saturation дают остановку
миссии и явный статус. Само Pause требует position hold; одной установки throttle=0
недостаточно. Automatic return/landing при fault не обещаем без соответствующего
контроллера. Этот маршрутный MVP здесь описан, но ещё не реализован.
